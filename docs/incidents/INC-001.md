# Incident RCA: INC-001 / SP-104 (The Empty Export)

- **Incident ID**: INC-001
- **Tracking Ticket**: SP-104
- **Date**: 2026-10-09
- **Severity**: P1 / High
- **Owner**: Data Platform & Ingestion Engineering
- **Status**: Resolved

---

## 1. Summary

An enterprise client transitioned to a new export tool on Monday. Over the next two nightly runs, the SupportPilot ingestion pipeline reported complete success (exit code `0`, no errors), but wrote 0 records to `valid.jsonl` while dumping 100% of records into `rejects.jsonl`. Because the process exited with code `0`, no monitoring alerts triggered and nobody inspected the output for two days. Downstream analytics dashboards remained empty until flagged by Meera. The client's weekly report was due Friday and Rohan's evaluation dataset was missing.

---

## 2. Timeline

- **Monday**: Client switched export tools. First nightly ingestion job ran; produced 0 valid records, 100% rejections, and exited `0`.
- **Tuesday**: Second nightly batch repeated 100% rejection, exiting `0`. Downstream dashboards remained empty; no alerts fired.
- **Incident Discovery**: Meera discovered empty dashboards. Priya Raman escalated incident INC-001 / SP-104.
- **Investigation & Triage**: Pipeline behavior reproduced locally using `data/incident_export.jsonl` created via `text.encode('utf-16')`. Byte-level inspection confirmed UTF-16LE encoding with BOM.
- **Remediation**: Implemented streaming multi-encoding support, typed exceptions, small-file rejection guards, unrounded threshold checks, standardized exit codes, and PII-safe summary telemetry.

---

## 3. Root Cause Analysis

### Byte-Level Evidence

Inspecting the client export file (`data/incident_export.jsonl`) at the byte level reveals:

```text
$ hexdump -C data/incident_export.jsonl | head -n 4
00000000  ff fe 7b 00 22 00 74 00  69 00 63 00 6b 00 65 00  |..{.".t.i.c.k.e.|
00000010  74 00 5f 00 69 00 64 00  22 00 3a 00 20 00 22 00  |t._.i.d.". .".|
00000020  54 00 2d 00 31 00 30 00  30 00 31 00 22 00 2c 00  |T.-.1.0.0.1.".,.|
00000030  20 00 22 00 63 00 75 00  73 00 74 00 6f 00 6d 00  | ."c.u.s.t.o.m.|
```

1. **Byte Order Mark (BOM)**: The first two bytes are `\xff\xfe` (UTF-16LE BOM).
2. **Interleaved Null Bytes**: Each ASCII character code point is stored as 2 bytes (e.g. `{` is `0x7b 0x00`, `"` is `0x22 0x00`).
3. **Two-Stage Failure Cascade**:
   - The legacy loader used binary `readline()` expecting single-byte `0x0a` (`\n`) and assumed UTF-8.
   - **Line 1**: The leading `\xff\xfe` failed UTF-8 decoding, logging `invalid_encoding`.
   - **Lines 2–10**: Reading stopped at `0x0a`, but because UTF-16LE newline is `0x0a 0x00`, each subsequent chunk left trailing or leading `0x00` null bytes across JSON keys and values. The parser failed with `invalid_json` on every line.
   - All 10 lines were rejected into `rejects.jsonl`, but the process exited `0`.

---

## 4. Why Detection Failed

1. **Permissive Success Code**: The CLI treated record-level rejections as benign line skips, exiting `0` even when every single line failed.
2. **Missing Rate Guard**: The pipeline had no guard against abnormally high rejection rates.
3. **Missing Health Telemetry**: The CLI wrote only unstructured text to stdout, with no machine-readable JSON metrics for alerting pipelines.

---

## 5. Architectural Decisions & Rationale

| Decision | Choice | Rationale |
|---|---|---|
| **Encoding Support** | UTF-16LE / UTF-16BE with BOM | Peeks first 2–4 bytes using `file.peek(4)` without reading the entire file into memory. Streams chunked buffers aligned to 2-byte delimiters (`b"\x0a\x00"` or `b"\x00\x0a"`). |
| **Non-BOM UTF-16** | Loud File-Level Rejection | Files lacking a BOM with alternating null bytes (`header[0] == 0 or header[1] == 0`) fail loudly with `UnsupportedEncodingError` and exit code `2`. Ambiguous multi-byte formats without BOM must not be guessed. |
| **Typed Exceptions** | Domain Exception Hierarchy | Replaced string message matching with explicit exception classes: `EmptyFileError`, `BlankFileError`, `UnsupportedEncodingError`, and `PathConflictError` (subclassing `ValueError`). |
| **Small-File Guard** | 100% Rejection Fail-Safe | Added guard: `valid == 0` with `total > 0` always exits code `3` regardless of sample size. Prevents small-scale silent failures (e.g. 3-line or 15-line exports). |
| **Reject-Rate Guard** | `--max-reject-rate` (default: `0.5`) | Evaluated when `total_records >= 20` (`--min-records 20`) using unrounded comparison (`raw_reject_rate > max_reject_rate`). Strict inequality ensures exact boundary values (e.g. 50.0%) pass. |
| **Exit Codes** | Standardized 4-State Contract | `0` = OK;<br>`1` = Unhandled crash;<br>`2` = Bad or empty file (0 bytes, blank-only, non-BOM UTF-16, unreadable, path conflict);<br>`3` = Reject rate too high (or zero valid records, or `--fail-on-rejects`). |
| **`--fail-on-rejects`** | Moved from Exit `2` to `3` | **Breaking change**: In SP-101 `--fail-on-rejects` exited `2`. It now exits `3` to align with the new standardized exit code contract where `2` is reserved for bad/empty files and `3` represents rejection guard triggers. |
| **Overwrite Guard** | `PathConflictError` Exits `2` | Attempting to overwrite destination files (`valid.jsonl`, `rejects.jsonl`, `report.json`) raises `PathConflictError` and exits code `2` with a clear error on stderr. |
| **Crash Safety & PII** | Exception Class Only | The crash handler prints `Fatal crash: {exc.__class__.__name__}` to stderr. Exception payload text is never printed, preventing raw ticket data from leaking during unexpected errors. |
| **Monitoring Summary** | PII-Free JSON Line | Emits exactly one JSON line to stdout upon termination: `{"total": int, "valid": int, "invalid": int, "reject_rate": float, "elapsed": float, "exit_reason": str}`. Strictly zero ticket content, customer data, or ticket IDs. |

## 6. The Fix & Performance Verification

1. **Loader Implementation (`supportpilot/ingestion/loader.py`)**:
   - Added `_read_utf16_raw_lines()` streaming 64 KB buffers with 2-byte aligned newline splitting and 1 MB line guard.
   - Retained fast native `readline()` for UTF-8 files.
   - Implemented typed exceptions (`EmptyFileError`, `BlankFileError`, `UnsupportedEncodingError`, `PathConflictError`).
2. **CLI Guard Implementation (`supportpilot/ingestion/__main__.py`)**:
   - Added `--max-reject-rate` and `--min-records`.
   - Added zero-valid fail-safe (`valid == 0 and total > 0`).
   - Standardized exit codes (`0, 1, 2, 3`) and unrounded comparison.
   - Implemented PII-safe crash handling and JSON summary line.
3. **1M-Record Benchmark Verification (`/usr/bin/time -l`)**:
   - **SP-101 Baseline (1,000,000 records, 139 MB file)**: `9.38 s` real time, `140.64 MB` max RSS (`140,640,256 bytes`).
   - **SP-104 Post-Fix Run (1,000,000 records, 150 MB file)**: `8.78 s` real time, `152.76 MB` max RSS (`160,186,368 bytes`).
   - **Result**: Ingestion is ~6.4% faster and memory remains flat within 8.6% delta, well within the 10% threshold.

## 7. Prevention & Proposed Follow-ups

1. **CI Encoding & Rate Tests**: 13 comprehensive tests in `tests/test_loader.py` covering UTF-16 LE/BE, non-BOM rejection, boundary thresholds, small-file zero-valid rejection, overwrite refusal, empty/blank files, exit codes, PII-safe summaries, and baseline byte-identity.
2. **Downstream Alerting** (*Proposed follow-up, Owner: Dev / Platform*): Configure workflow orchestrator (Airflow / Cron) to alert immediately on any non-zero exit code (`2` or `3`).
3. **Operational Metric Scraping** (*Proposed follow-up, Owner: Dev / Platform*): Update batch job wrapper to parse the stdout JSON summary line and publish `reject_rate` and `elapsed` metrics to the telemetry stack.
4. **Export Validation** (*Proposed follow-up, Owner: Dev*): Provide clients with an automated pre-flight validation utility to detect unsupported encodings before batch submission.
