# Incident RCA: INC-001 / SP-104 (The Empty Export)

- **Incident ID**: INC-001
- **Tracking Ticket**: SP-104
- **Date**: 2026-10-09
- **Severity**: P1 / High
- **Owner**: Data Platform & Ingestion Engineering
- **Status**: Resolved

---

## 1. Summary

On Monday, an enterprise client transitioned to a new export tool. During the subsequent nightly ingestion runs, the SupportPilot ingestion pipeline completed with exit code `0` (success), but produced 0 valid records in `valid.jsonl` and rejected 100% of incoming records into `rejects.jsonl`. Because the pipeline exited successfully without error alarms, downstream analytics dashboards remained silently empty for two consecutive days until flagged by Meera during business review.

---

## 2. Timeline

- **Monday**: Client switches export tooling. Nightly ingestion batch processes export file, reports 0 valid records, 100% rejections, and exits `0`.
- **Tuesday**: Second nightly batch repeats silent 100% rejection, exiting `0`. Downstream dashboard remains unpopulated; no automated alerts trigger.
- **Thursday 08:00**: Meera notices missing metrics and empty dashboards. Rohan's evaluation dataset is confirmed missing.
- **Thursday 08:15 (Triage)**: Reproduced locally using client export replica (`data/incident_export.jsonl`). Hex inspection proves UTF-16LE encoding with BOM.
- **Thursday 11:30 (Fix & Testing)**: Streaming UTF-16 BOM detection, reject-rate guards, exit codes, and JSON monitoring summary implemented and verified across unit and regression tests.

---

## 3. Root Cause Analysis

### Byte-Level Evidence

Inspecting the client's export file (`data/incident_export.jsonl`) at the byte level reveals:

```text
$ hexdump -C data/incident_export.jsonl | head -n 4
00000000  ff fe 7b 00 22 00 74 00  69 00 63 00 6b 00 65 00  |..{.".t.i.c.k.e.|
00000010  74 00 5f 00 69 00 64 00  22 00 3a 00 20 00 22 00  |t._.i.d.". .".|
00000020  54 00 2d 00 31 00 30 00  30 00 31 00 22 00 2c 00  |T.-.1.0.0.1.".,.|
00000030  20 00 22 00 63 00 75 00  73 00 74 00 6f 00 6d 00  | ."c.u.s.t.o.m.|
```

1. **Byte Order Mark (BOM)**: The first two bytes are `\xff\xfe` (UTF-16LE BOM).
2. **Interleaved Null Bytes**: Each ASCII character code point is stored as 2 bytes (e.g. `{` is `0x7b 0x00`, `"` is `0x22 0x00`).
3. **Naive UTF-8 Splitting**: The legacy loader used binary `readline()` expecting single-byte `0x0a` (`\n`) and decoded each line with UTF-8. The first line encountered `\xff\xfe` and failed with `invalid_encoding`. Subsequent lines split on `0x0a`, leaving `0x00` null bytes across JSON strings, failing JSON deserialization with `invalid_json`.

---

## 4. Why Detection Failed

1. **Permissive Exit Code**: The ingestion CLI was designed to isolate bad records into `rejects.jsonl` while exiting `0`. There was no threshold guard checking whether the proportion of rejected records was abnormally high.
2. **Absence of Rate Guards**: The pipeline treated a batch where 100% of records failed identically to a batch where 0.01% failed due to typos.
3. **No Machine-Readable Health Telemetry**: The CLI logged human-oriented strings to stdout without structured JSON metrics that operational alerting tools (Datadog, CloudWatch, Prometheus) could parse.

---

## 5. Architectural Decisions & Rationale

| Decision | Choice | Rationale |
|---|---|---|
| **Encoding Support** | UTF-16LE / UTF-16BE with BOM | Peeks first 2–4 bytes using `file.peek(4)` without loading the file into memory. Stream decodes chunked buffers aligned to 2-byte delimiters (`b"\x0a\x00"` or `b"\x00\x0a"`). |
| **Non-BOM UTF-16** | Loud File-Level Rejection | Files lacking a BOM with alternating null bytes (`header[0] == 0 or header[1] == 0`) fail immediately with `ValueError("UTF-16 without BOM is not supported")` and exit code `2`. Ambiguous multi-byte formats without BOM must not be guessed. |
| **Reject-Rate Guard** | `--max-reject-rate` (default: `0.5`) | Evaluated only when `total_records >= 20` (`--min-records 20`). Small batches (< 20 records) exhibit high statistical variance (e.g. our 10-record sample with 60% failure rate). Strict inequality (`reject_rate > max_reject_rate`) ensures exact boundary values (e.g. 50.0%) pass. |
| **Exit Codes** | Standardized 4-state contract | `0` = OK;<br>`1` = Unhandled crash / exception;<br>`2` = Bad or empty file (0 bytes, blank-only lines, non-BOM UTF-16, unreadable);<br>`3` = Reject rate too high (or `--fail-on-rejects`). |
| **Edge Inputs** | Empty & Blank Files Exit `2` | An empty file (0 bytes) or a file containing only whitespace/blank lines represents missing or corrupted upstream exports, not a successful 0-record run. |
| **Monitoring Summary** | PII-Free JSON Line | Exactly one JSON object printed to stdout upon termination: `{"total": int, "valid": int, "invalid": int, "reject_rate": float, "elapsed": float, "exit_reason": str}`. Never leaks ticket bodies, customer data, or ticket IDs. |

---

## 6. The Fix

1. **Streaming Multi-Encoding Reader (`supportpilot/ingestion/loader.py`)**:
   - Added `_read_utf16_raw_lines()` to stream UTF-16 files in 64 KB buffers, splitting strictly on 2-byte-aligned newline delimiters while enforcing the 1 MB line guard.
   - Preserved fast native `readline()` for UTF-8 files, maintaining zero regression on the 1M-record benchmark.
   - Added validation in `process_file()` to reject empty files and blank-only files as `ValueError`.
2. **CLI Guards & Exit Code Contract (`supportpilot/ingestion/__main__.py`)**:
   - Added `--max-reject-rate` (default `0.5`) and `--min-records` (default `20`).
   - Implemented exit codes `0` (ok), `1` (crash), `2` (bad/empty file), `3` (threshold exceeded).
   - Added `_emit_summary()` printing the single JSON operational summary line to stdout.

---

## 7. Prevention & Follow-ups

1. **CI Encoding & Rate Tests**: 11 new tests added covering UTF-16 LE/BE, non-BOM rejection, boundary thresholds, empty/blank files, exit codes, and PII-free summary output.
2. **Downstream Alerting**: Orchestrator (Airflow / Cron) configured to alert on any non-zero exit code (`2` or `3`).
3. **Metric Scraping**: Ingestion runner configured to parse the final JSON summary line and publish `reject_rate` and `elapsed` metrics to the monitoring stack.
